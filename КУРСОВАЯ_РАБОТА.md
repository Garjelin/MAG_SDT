# ВВЕДЕНИЕ

## Актуальность темы

В современном мире информационные технологии играют ключевую роль в автоматизации бизнес-процессов различных предприятий. Книжная торговля не является исключением и требует эффективных систем управления товарными запасами, обработки заказов и взаимодействия с покупателями.

Традиционные методы ведения учета в книжных магазинах, основанные на бумажных журналах и ручном труде, имеют ряд существенных недостатков:
- Высокая вероятность ошибок при ручном вводе данных
- Сложность поиска информации о наличии книг
- Отсутствие автоматического уведомления покупателей о поступлении товаров
- Невозможность быстрого анализа статистики продаж
- Большие временные затраты на обслуживание покупателей

Автоматизация процессов книжного магазина позволяет:
- Повысить эффективность работы персонала
- Сократить время обслуживания покупателей
- Минимизировать ошибки в учете товаров
- Автоматически уведомлять покупателей о поступлении интересующих книг
- Анализировать статистику продаж и спроса
- Улучшить качество обслуживания клиентов

Таким образом, разработка программного обеспечения для автоматизации работы книжного магазина является актуальной задачей, решение которой способствует повышению конкурентоспособности предприятия.

# ОПИСАНИЕ ПРЕДМЕТНОЙ ОБЛАСТИ

## Общее описание

**Книжный магазин** - это торговое предприятие, специализирующееся на розничной продаже книжной продукции. Основная деятельность книжного магазина заключается в закупке книг у издательств и дистрибьюторов, формировании ассортимента и продаже книг конечным покупателям.

Основные участники бизнес-процессов:
- **Администратор** - сотрудник магазина, отвечающий за управление каталогом, обработку заказов, работу с покупателями
- **Покупатель** - клиент магазина, осуществляющий поиск и покупку книг

Ключевые сущности предметной области:
- **Книга** - товарная единица, содержащая информацию об авторе, названии, издательстве, годе издания, цене и количестве в наличии
- **Покупатель** - физическое лицо, зарегистрированное в системе с контактными данными
- **Заказ** - заявка покупателя на приобретение книги с определенным статусом
- **Запись в базе ожидания** - регистрация запроса покупателя на отсутствующую книгу
- **Каталог** - структурированная коллекция всех книг магазина

## Основные бизнес-процессы

### 1. Управление каталогом

Процесс поддержания актуальной информации о книгах в магазине включает:

**Добавление новых книг:**
- Администратор получает информацию о новом поступлении
- Вносит данные о книге в систему (автор, название, издательство, год, цена, количество)
- Система автоматически проверяет базу ожидания
- При наличии ожидающих покупателей - отправляются уведомления

**Обновление информации:**
- Изменение цены книги
- Корректировка данных об издании
- Обновление количества при поступлении товара

**Списание и удаление:**
- Уменьшение количества при продаже
- Удаление книг, снятых с продажи

\newpage

### 2. Обслуживание покупателей

Процесс взаимодействия с клиентами магазина:

**Регистрация покупателя:**
- Внесение контактных данных (ФИО, email, телефон)
- Создание профиля в системе
- Возможность просмотра истории заказов

**Консультация и поиск:**
- Помощь в поиске нужной книги по каталогу
- Проверка наличия книги
- Предоставление информации о цене и характеристиках

**Оформление покупки:**
- Создание заказа в системе
- Резервирование книги
- Обработка оплаты и выдача товара

### 3. Работа с заказами

Центральный бизнес-процесс системы:

**Создание заказа при наличии книги:**
```
1. Покупатель выбирает книгу из каталога
2. Система проверяет наличие (quantity > 0)
3. Создается заказ со статусом "Доступна" или "Завершен"
4. Количество книги уменьшается
5. Покупатель получает книгу
```

**Создание заказа при отсутствии книги:**
```
1. Покупатель выбирает книгу из каталога
2. Система проверяет наличие (quantity = 0)
3. Создается заказ со статусом "В ожидании"
4. Покупатель автоматически добавляется в базу ожидания
5. При поступлении книги покупатель получает уведомление
6. Статус заказа меняется на "Доступна"
7. Администратор завершает заказ при выдаче книги
```

### 4. Система уведомлений

Автоматический процесс информирования покупателей:

**При поступлении книги:**
- Система проверяет базу ожидания для данной книги
- Находит всех ожидающих покупателей
- Отправляет уведомления каждому покупателю
- Помечает записи как "Уведомлено"
- Обновляет статусы связанных заказов с "В ожидании" на "Доступна"

\newpage

## UML-диаграммы проектирования

### 3.3.1. Use Case диаграмма

Use Case диаграмма отображает функциональные требования к системе с точки зрения пользователей.

```
[СКРИНШОТ: Use Case диаграмма]

Описание диаграммы:
- Актеры: Администратор, Покупатель
- Use Cases для Администратора:
  * Управление каталогом (включает: добавить/редактировать/удалить книгу)
  * Управление покупателями (включает: добавить/редактировать/удалить покупателя)
  * Управление заказами (включает: создать/завершить/отменить заказ)
  * Просмотр базы ожидания
  * Просмотр статистики
  * Переключение роли

- Use Cases для Покупателя:
  * Просмотр каталога
  * Поиск книг
  * Создание заказа
  * Просмотр своих заказов
  * Переключение роли

- Связи:
  * Администратор наследует все функции Покупателя (отношение обобщения)
  * "Создать заказ" extends "Добавить в базу ожидания" (при отсутствии книги)
  * "Обновить количество книги" extends "Уведомить покупателей" (автоматически)
```

**Ключевые прецеденты использования:**

1. **UC-1: Создание заказа (есть в наличии)**
   - Актер: Администратор/Покупатель
   - Предусловие: Книга присутствует в каталоге с quantity > 0
   - Основной сценарий:
     1. Пользователь выбирает "Создать заказ"
     2. Выбирает покупателя из списка
     3. Выбирает книгу из каталога
     4. Указывает количество
     5. Система проверяет наличие
     6. Система создает заказ со статусом "Завершен"/"Доступна"
     7. Система уменьшает количество книги
   - Постусловие: Заказ создан, количество книги уменьшено

2. **UC-2: Создание заказа (нет в наличии)**
   - Актер: Администратор/Покупатель
   - Предусловие: Книга отсутствует (quantity = 0)
   - Основной сценарий:
     1. Пользователь выбирает "Создать заказ"
     2. Выбирает покупателя и книгу
     3. Система проверяет наличие
     4. Система создает заказ со статусом "В ожидании"
     5. Система добавляет покупателя в базу ожидания
     6. Покупатель получает информацию о постановке в очередь
   - Постусловие: Заказ в ожидании, покупатель в базе ожидания

### 3.3.2. Class диаграмма

Class диаграмма описывает статическую структуру системы, показывая классы, их атрибуты, методы и взаимосвязи.

```
[СКРИНШОТ: Class диаграмма]

Основные классы и их атрибуты:

┌─────────────────────────────┐
│         Book                │
├─────────────────────────────┤
│ - id: Int                   │
│ - author: String            │
│ - title: String             │
│ - publisher: String         │
│ - publicationYear: Int      │
│ - price: Double             │
│ - quantity: Int             │
├─────────────────────────────┤

### 3.3.3. Sequence диаграмма

Sequence диаграмма описывает взаимодействие объектов во времени для сценария "Создание заказа на отсутствующую книгу".

```
[СКРИНШОТ: Sequence диаграмма - Создание заказа на отсутствующую книгу]

Участники:
- :User (Пользователь)
- :OrderScreen (UI экран заказов)
- :BookShopRepository (Репозиторий)
- :Catalog (Каталог)

- :Order (Заказ)

- :Customer (Покупатель)

Последовательность взаимодействий:

1. User -> OrderScreen: нажимает "Создать заказ"
2. OrderScreen -> User: отображает диалог выбора покупателя
3. User -> OrderScreen: выбирает покупателя
4. OrderScreen -> User: отображает диалог выбора книги
5. User -> OrderScreen: выбирает книгу, указывает количество
6. OrderScreen -> BookShopRepository: createOrder(customerId, bookId, quantity)
7. BookShopRepository -> Catalog: getBookById(bookId)
8. Catalog --> BookShopRepository: book
9. BookShopRepository -> Book: isAvailable()
10. Book --> BookShopRepository: false (quantity = 0)
11. BookShopRepository -> Order: new Order(id, customerId, bookId)
12. BookShopRepository -> Order: placeOrder(false)

14. Order --> BookShopRepository: WAITING
15. BookShopRepository -> WaitingList: addToWaiting(customer, book)
16. WaitingList -> WaitingListRecord: new Record(...)
17. WaitingList --> BookShopRepository: record
18. BookShopRepository -> DataManager: saveData(appData)
19. DataManager --> BookShopRepository: true
20. BookShopRepository --> OrderScreen: order
21. OrderScreen -> User: "Книги нет в наличии. Вы добавлены в базу ожидания"

Alt [При поступлении книги]:
  22. BookShopRepository -> Catalog: updateCatalog(bookId, quantity)
  23. Catalog -> Book: increaseQuantity(quantity)
  24. BookShopRepository -> WaitingList: notifyCustomers(book, customers)
  25. WaitingList -> Customer: receiveNotification(bookTitle)
  26. WaitingList -> WaitingListRecord: markAsNotified()
  27. BookShopRepository -> Order: markAsAvailable()
  28. Order -> Order: status = AVAILABLE

### 3.3.4. Activity диаграмма

Activity диаграмма отображает поток действий в процессе "Оформление заказа с учетом базы ожидания".

```
[СКРИНШОТ: Activity диаграмма - Процесс оформления заказа]

Swimlanes (участники):
- Покупатель
- Система
- Администратор

Поток действий:

[Покупатель]
  (Начало) -> [Поиск книги в каталоге]
  -> [Выбор книги]
  -> [Указание количества]

[Система]
  -> <Проверка наличия>
  
  Decision: Книга доступна?
  
  [ДА] -> [Создание заказа (AVAILABLE/COMPLETED)]
       -> [Уменьшение количества книги]
       -> [Резервирование книги]
       -> [Уведомление покупателя]
       -> (Конец: Заказ выполнен)
  
  [НЕТ] -> [Создание заказа (WAITING)]
       -> [Добавление в базу ожидания]
       -> [Уведомление о постановке в очередь]
       -> [Ожидание поступления]
       
       -> <Ожидание поступления книги>
       
[Администратор]
       -> [Поступление книги]
       -> [Обновление количества]

[Система]
       -> [Проверка базы ожидания]
       -> <Есть ожидающие?>
       
       [ДА] -> Fork (параллельные действия):
            -> [Отправка уведомлений покупателям]
            -> [Обновление статусов заказов WAITING->AVAILABLE]
            -> [Пометка записей как "Уведомлено"]
            -> Join
            -> [Уведомление администратора]
       
       [НЕТ] -> (Конец: Обновление завершено)

[Покупатель]
       -> [Получение уведомления]
       -> [Приход в магазин]

[Администратор]
       -> [Проверка заказа]
       -> [Выдача книги]
       -> [Завершение заказа]
       -> (Конец: Заказ выполнен)
```

**Примечания к диаграмме:**
- Decision nodes (ромбы) представляют точки принятия решений
- Fork/Join показывают параллельное выполнение действий
- Swimlanes разделяют ответственность между участниками процесса
- Переходы между swimlanes показывают передачу управления

│             │                       │                       │

│             │                       │                       │
│             ↓                       ↓                       │
│      ┌────────────┐          ┌──────────┐                 │
│      │ AVAILABLE  │          │ WAITING  │  (В ожидании)   │
│      │(Доступна)  │          └──────────┘                 │
│      └────────────┘                 │                       │
│             │                       │                       │

│             │                       │                       │
│             │                       ↓                       │
│             │              ┌──────────────┐                │

│             └───────────┬───────────┘                      │
│                         │                                   │
│                  [Администратор                            │
│                   завершает заказ]                         │
│                         │                                   │
│                         ↓                                   │
│                  ┌────────────┐                            │
│                  │ COMPLETED  │  (Завершен)                │
│                  └────────────┘                            │
│                         │                                   │
│                         ↓                                   │
│                       [Конец]                              │
│                         ●                                   │
│                                                             │
│  Из любого активного состояния:                           │
│                         │                                   │
│                  [Отмена заказа]                           │
│                         │                                   │
│                         ↓                                   │
│                  ┌────────────┐                            │
│                  │ CANCELLED  │  (Отменен)                 │
│                  └────────────┘                            │
│                         │                                   │
│                         ↓                                   │
│                       [Конец]                              │
│                         ●                                   │
└─────────────────────────────────────────────────────────────┘

Переходы и условия:

1. CREATED -> AVAILABLE
   - Условие: Книга в наличии (quantity > 0)
   - Действие: Уменьшить quantity книги

2. CREATED -> WAITING
   - Условие: Книга отсутствует (quantity = 0)
   - Действие: Добавить покупателя в базу ожидания

3. WAITING -> AVAILABLE
   - Условие: Книга поступила в магазин
   - Триггер: updateCatalog(bookId, quantity) с quantity > 0
   - Действие: Уведомить покупателя

4. AVAILABLE -> COMPLETED
   - Условие: Администратор завершает заказ
   - Действие: Списать книгу со склада (decreaseQuantity)

5. * -> CANCELLED
   - Условие: Пользователь или администратор отменяет заказ
   - Ограничение: Только из активных состояний (не COMPLETED, не CANCELLED)

Внутренние действия состояний:

State WAITING:
  entry / Добавить в базу ожидания
  do / Ожидание поступления
  
State AVAILABLE:
  entry / Зарезервировать книгу
  do / Ожидание выдачи
  
State COMPLETED:
  entry / Обновить статистику
  exit / Архивировать заказ
```

### 4.2.2. Применение паттернов проектирования

**1. Repository Pattern**

Паттерн Repository обеспечивает централизованный доступ к данным и абстрагирует детали хранения.

```kotlin
class BookShopRepository {
    private val dataManager = DataManager()
    private var appData: AppData = dataManager.loadData()
    
    // Единая точка доступа к данным
    fun addBook(...): Book { ... }
    fun createOrder(...): Order? { ... }
    fun addCustomer(...): Customer { ... }
    
    // Автоматическое сохранение
    private fun save() {
        if (autoSave) dataManager.saveData(appData)
    }
}
```

**Преимущества:**
- UI слой не знает о деталях хранения (JSON, DB, etc)
- Легко заменить способ хранения без изменения UI
- Централизованная бизнес-логика

**2. Singleton Pattern**

Используется для обеспечения единственного экземпляра объектов с глобальным доступом.

```kotlin
object RoleManager {
    private val _currentRole = mutableStateOf(UserRole.ADMIN)
    val currentRole: State<UserRole> = _currentRole
    
    fun setRole(role: UserRole) {
        _currentRole.value = role
    }
}
```

**Применение:**
- RoleManager - управление текущей ролью пользователя
- BookShopRepository - централизованный доступ к данным

**3. Observer Pattern (через Compose State)**

Реактивное обновление UI при изменении данных.

```kotlin
// В Repository
var onDataChanged: (() -> Unit)? = null

private fun save() {
    dataManager.saveData(appData)
    onDataChanged?.invoke()  // Уведомление подписчиков
}

// В UI
LaunchedEffect(Unit) {
    repository.onDataChanged = {
        books = repository.getAllBooks()  // Автоматическое обновление
    }
}
```

**4. Strategy Pattern (для сортировки)**

Различные стратегии сортировки книг.

```kotlin
enum class SortOption {
    TITLE, AUTHOR, PRICE_ASC, PRICE_DESC, YEAR_ASC, YEAR_DESC
}

when (sortOption) {
    SortOption.TITLE -> books.sortedBy { it.title }
    SortOption.PRICE_ASC -> books.sortedBy { it.price }
    SortOption.PRICE_DESC -> books.sortedByDescending { it.price }
    // ...
}
```

**5. Factory Pattern (в создании объектов)**

Централизованное создание объектов с генерацией ID.

```kotlin
fun addBook(...): Book {
    val book = appData.catalog.addBook(...)  // Factory метод в Catalog
    save()
    return book
}
```

## Ключевые технические решения

### 4.4.1. Автоматическая система уведомлений

Одна из ключевых особенностей системы - автоматическое уведомление покупателей при поступлении книг.

**Алгоритм работы:**

1. При обновлении количества книги (через updateBookQuantity или addBook):
   ```kotlin
   fun updateBookQuantity(bookId: Int, quantity: Int) {
       catalog.updateCatalog(bookId, quantity)
       val book = catalog.getBookById(bookId)
       book?.let { checkWaitingListForBook(it) }
       save()
   }
   ```

2. Проверка базы ожидания:
   ```kotlin
   private fun checkWaitingListForBook(book: Book) {
       if (!book.isAvailable()) return
       
       val notified = waitingList.notifyCustomers(book, customers)
       
       if (notified.isNotEmpty()) {
           // Обновление статусов заказов
           orders.filter { it.bookId == book.id && it.status == WAITING }
               .forEach { it.markAsAvailable() }
       }
   }
   ```

3. Уведомление покупателей:
   ```kotlin
   fun notifyCustomers(book: Book, customers: List<Customer>): List<Customer> {
       val waiting = records.filter { it.bookId == book.id && !it.notified }
       
       return waiting.mapNotNull { record ->
           customers.find { it.id == record.customerId }?.also {
               it.receiveNotification(book.title)
               record.markAsNotified()
           }
       }
   }
   ```

**Преимущества:**
- Полностью автоматический процесс
- Покупатель не пропустит поступление
- Снижается нагрузка на персонал

### 5.4.7. Фильтрация и сортировка

**Чекбокс "Только в наличии":**
- Включен: показываются только книги с quantity > 0
- Выключен: показываются все книги

**Сортировка (6 вариантов):**

1. **По названию (А→Я)**
   - Алфавитный порядок названий
   - По умолчанию

2. **По автору (А→Я)**
   - Алфавитный порядок фамилий авторов
   - Группирует книги одного автора

3. **По году издания (новые → старые)**
   - Сначала 2022, потом 2021, 2020...
   - Для поиска новинок

4. **По году издания (старые → новые)**
   - Сначала старые издания
   - Для антикварных книг

5. **По цене (возрастание)**
   - От самых дешевых к дорогим
   - Для экономных покупателей

6. **По цене (убывание)**
   - От самых дорогих к дешевым
   - Для просмотра коллекционных изданий

**Комбинирование:**
Поиск, фильтр и сортировка работают вместе:

```
Поиск: "толстой"
Фильтр: ☑ Только в наличии
Сортировка: По цене (возрастание)

Результат: Книги Толстого в наличии, от дешевых к дорогим
```

### 5.6.3. Логика создания заказа

После нажатия "Создать заказ" система выполняет следующие действия:

**Если книга В НАЛИЧИИ (quantity >= заказанное количество):**

1. Создается заказ с ID
2. Статус заказа: **COMPLETED** (сразу завершен)
3. Количество книги уменьшается на заказанное
4. Показывается уведомление:

```
✅ Заказ создан!

Заказ #13 успешно создан и завершен.

Покупатель: Иванов Иван Иванович
Книга: "Война и мир (4 тома)" × 2 шт.
Сумма: 2500₽

Количество книги: 8 → 6 шт.
```

**Если книги НЕТ в наличии (quantity < заказанное количество):**

1. Создается заказ с ID
2. Статус заказа: **WAITING** (в ожидании)
3. Покупатель автоматически добавляется в базу ожидания
4. Показывается уведомление:

```
⏳ Заказ создан (в ожидании)

Заказ #14 создан со статусом "В ожидании".

Покупатель: Смирнов Алексей Викторович
Книга: "Доктор Живаго" × 1 шт.
Сумма: 680₽

📋 Покупатель добавлен в базу ожидания.
При поступлении книги он получит автоматическое
уведомление, и статус заказа изменится на "Доступна".
```

### 5.7.2. Фильтры базы ожидания

**Варианты фильтра:**

3. **Уведомленные** - только уведомленные (notified = true)
4. **По книге** - фильтр по конкретной книге
5. **По покупателю** - фильтр по конкретному покупателю

**Счетчики:**

```

Активных (ожидают): 2

```

### 5.7.3. Автоматические уведомления

Система автоматически уведомляет покупателей при поступлении книги.

**Когда происходит:**

1. Администратор добавляет книгу с quantity > 0
2. Администратор обновляет количество существующей книги
3. Администратор редактирует книгу и увеличивает количество

**Что происходит автоматически:**

1. Система находит все записи в базе ожидания для этой книги
2. Для каждой записи (где notified = false):
   - Покупатель получает уведомление
   - Запись помечается как notified = true
   - Устанавливается дата уведомления
3. Связанные заказы меняют статус WAITING → AVAILABLE
4. Показывается сообщение администратору:

```
✅ Покупатели уведомлены!

Книга: "Преступление и наказание"
Уведомлено покупателей: 1

• Сидоров Петр Александрович
  Email: sidorov@example.com
  Заказ #3 изменен: В ожидании → Доступна
```

data class Book(
    val id: Int,

    /**
     * Уменьшить количество книг при продаже
     */
    fun decreaseQuantity(count: Int = 1): Boolean {
        return if (quantity >= count) {
            quantity -= count
            true
        } else {
            false
        }
    }
    
    /**
     * Увеличить количество книг при поступлении
     */
    fun increaseQuantity(count: Int = 1) {
        require(count > 0) { "Количество должно быть положительным" }
        quantity += count
    }
}

@Serializable
enum class OrderStatus {
    CREATED,      // Создан
    WAITING,      // В ожидании (книга отсутствует)
    AVAILABLE,    // Доступна (книга поступила)
    COMPLETED,    // Завершен
    CANCELLED     // Отменен
}

@Serializable
data class Order(
    val id: Int,
    val customerId: Int,
    val bookId: Int,
    val creationDate: Long = System.currentTimeMillis(),
    var status: OrderStatus = OrderStatus.CREATED,
    var quantity: Int = 1,
    var lastUpdateDate: Long = System.currentTimeMillis()
) {
    /**
     * Оформить заказ
     */
    fun placeOrder(bookAvailable: Boolean): OrderStatus {
        status = if (bookAvailable) {
            OrderStatus.COMPLETED
        } else {
            OrderStatus.WAITING
        }
        lastUpdateDate = System.currentTimeMillis()
        return status
    }
    
    /**
     * Пометить книгу как доступную
     */
    fun markAsAvailable() {
        if (status == OrderStatus.WAITING) {
            updateStatus(OrderStatus.AVAILABLE)
        }
    }
}
```

/**
 * Обновить количество книги в каталоге

fun updateBookQuantity(bookId: Int, quantity: Int): Boolean {
    val result = appData.catalog.updateCatalog(bookId, quantity)
    if (result) {
        // Проверяем базу ожидания при поступлении книги
        val book = appData.catalog.getBookById(bookId)
        book?.let { checkWaitingListForBook(it) }
        save()
    }
    return result
}

/**
 * Проверить базу ожидания для конкретной книги
 * Уведомляет покупателей и обновляет заказы
 */
private fun checkWaitingListForBook(book: Book) {
    if (!book.isAvailable()) return
    
    // Уведомляем покупателей из базы ожидания
    val notifiedCustomers = appData.waitingList.notifyCustomers(
        book, 
        appData.customers
    )
    
    if (notifiedCustomers.isNotEmpty()) {
        println("✓ Уведомлено покупателей: ${notifiedCustomers.size}")
        
        // Обновляем статусы заказов
        appData.orders
            .filter { it.bookId == book.id && it.status == OrderStatus.WAITING }
            .forEach { it.markAsAvailable() }
    }
}
